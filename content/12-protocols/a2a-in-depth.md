> [!tldr]
> The A2A 1.0 specification has three layers: a data model defined in Protocol Buffers, abstract operations, and bindings that map those operations onto JSON-RPC, gRPC or HTTP+JSON. Around that core sit the parts that matter in production: version headers, task and context identifiers, push notifications, signed agent cards, declared security schemes and URI-named extensions. The one thing to remember: the agent card is the contract, so verify it, cache it and follow exactly the interface, version and tenant it declares.

## Key ideas

- **Three layers, eleven operations.** The data model (task, message, agent card, part, artifact, extension) has one normative source, the Protocol Buffers file [`a2a.proto`](https://github.com/a2aproject/A2A/blob/v1.0.1/specification/a2a.proto); the abstract operations are send message, send streaming message, get, list and cancel task, subscribe to task, create, get, list and delete push notification configs, and get extended agent card; the JSON-RPC, gRPC and HTTP+JSON/REST bindings must behave identically, and custom bindings are named by a URI that changes with every breaking change ([A2A Protocol Specification](https://a2a-protocol.org/latest/specification/), sections 1.3, 1.4, 3.1, 5.1 and 5.8).
- **Versions are negotiated per request.** A protocol version is `Major.Minor`, and patch numbers never count: clients must send an `A2A-Version` header (or parameter) on every request, an empty value means 0.3, and an agent that does not support the requested version returns `VersionNotSupportedError` ([A2A Protocol Specification](https://a2a-protocol.org/latest/specification/), sections 3.6 and 14.2.1). Version 1.0.0 (12 March 2026) broke 0.3 code, among other changes by merging the push notification config types, aligning enums with ProtoJSON and modernizing the OAuth flows (device code and PKCE added; the specification keeps implicit and password only as deprecated options). Version 1.0.1 (26 May 2026, the latest release as of November 2026) made the HTTP+JSON binding prefer its own media type, `application/a2a+json` ([a2aproject/A2A releases](https://github.com/a2aproject/A2A/releases); [A2A Protocol Specification](https://a2a-protocol.org/latest/specification/), section 4.5.7).
- **Contexts group, tasks track, parts carry.** A `contextId` groups related tasks and messages and is opaque to clients; an agent may generate one, and must reject a client-supplied one it cannot accept rather than silently replace it, while a `taskId` is always generated by the server and a client may only send one that refers to an existing task. Each part is exactly one of `text`, `raw` (bytes, base64 in JSON), `url` or `data`, with an optional `filename` and `mediaType`, and tasks move through states from `TASK_STATE_SUBMITTED` to terminal ones, with `TASK_STATE_INPUT_REQUIRED` and `TASK_STATE_AUTH_REQUIRED` as interrupted states ([A2A Protocol Specification](https://a2a-protocol.org/latest/specification/), sections 3.4 and 4.1; [`a2a.proto` at v1.0.1](https://github.com/a2aproject/A2A/blob/v1.0.1/specification/a2a.proto)).
- **Three ways to follow a task, and in-task authorization.** Clients poll, stream (`TaskStatusUpdateEvent` and `TaskArtifactUpdateEvent`, delivered in order, with several streams per task allowed) or register webhooks that receive the same payloads; the agent must send the credentials the push config specifies and should block private and loopback webhook URLs to prevent server-side request forgery, while the client must check the webhook's authenticity. An agent that needs an OAuth token or a human approval mid-task moves it to `TASK_STATE_AUTH_REQUIRED`; the credential should reach the agent out of band, and if it does travel in band through a chain of agents, it should be bound to the agent that asked for it ([A2A Protocol Specification](https://a2a-protocol.org/latest/specification/), sections 3.5, 7.6 and 13.2).
- **The agent card: discovered, cached, signed.** Cards live at `/.well-known/agent-card.json` (or in catalogs, or are configured directly), should be served with `Cache-Control` and `ETag`, list `supportedInterfaces` in order of preference, and each interface may carry a `tenant` value that clients must repeat exactly in every request; authenticated callers can fetch a richer extended card. A card may be signed with JWS (RFC 7515) over its JCS-canonicalized form (RFC 8785), with the `signatures` field excluded, and it declares security schemes: API key, HTTP authentication, OAuth 2.0 (authorization code, client credentials and device code flows, plus the deprecated implicit and password flows), OpenID Connect and mutual TLS ([A2A Protocol Specification](https://a2a-protocol.org/latest/specification/), sections 4.5, 8.2 to 8.6 and 3.1.11).
- **Extensions and the wider family.** Extensions are named by URIs that should carry a version, declared in the card with a `required` flag and activated per request through a binding-specific mechanism (in HTTP, the `A2A-Extensions` header); a breaking change needs a new URI, an agent must not fall back to an older version automatically, and AP2, a protocol for agent payments, ships as one such extension ([A2A Protocol Specification](https://a2a-protocol.org/latest/specification/), section 4.6; [AP2 documentation](https://ap2-protocol.org/)). IBM's Agent Communication Protocol is now part of A2A, with a migration guide ([IBM Research](https://research.ibm.com/projects/agent-communication-protocol)), and A2A joined the Agentic AI Foundation in August 2026: the foundation announced it on 17 August, and the A2A blog of 27 August describes it as a Growth Stage project ([AAIF, “A2A joins AAIF’s open agentic stack” (2026)](https://aaif.io/blog/a2a-joins-aaif); [A2A blog, “A New Chapter for A2A: Joining the Agentic AI Foundation” (2026)](https://a2a-protocol.org/latest/blog/2026/08/27/a-new-chapter-for-a2a-joining-the-agentic-ai-foundation/); see [governance](#protocol-governance)).

## Planned visuals

- **`diagram`:** the three layers stacked, with each abstract operation linked to its JSON-RPC method, gRPC call and HTTP endpoint, so a reader sees one operation in all three bindings.
- **`sequence`:** in-task authorization: the client sends a message, the agent moves the task to `TASK_STATE_AUTH_REQUIRED`, the credential arrives out of band, and the client follows the rest through a stream or a webhook.
- **`stepper`:** signing and verifying an agent card: drop default values and the `signatures` field, canonicalize with JCS, sign with a key named by `kid` and `jku`, and repeat the steps to verify.

## Talk like an expert

Experts say **binding**, **interface**, **service parameter**, **contextId versus taskId**, **interrupted state**, **extended agent card**, **JCS canonicalization** and **required extension**. They read an agent card like an API contract and ask which binding, version, tenant and security scheme it commits the agent to before they write a line of client code.
