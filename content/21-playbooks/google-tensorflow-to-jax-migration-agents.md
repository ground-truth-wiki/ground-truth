> [!tldr]
> Google built a multi-agent system, with a planner, an orchestrator and a coder running on Gemini 3 Pro, to migrate internal deep learning models from TensorFlow to JAX. On six YouTube models the fully featured configuration was "the strongest configuration" on LLM-judged checklists, and on two in-production models the team writes "We estimate time savings of 6.4x-8x". The paper also says a perfect checklist score "does not guarantee correctness".

## The problem

Google "builds and operates thousands of machine learning models across its product suite", many on TensorFlow. The company is shifting to JAX, which the paper calls "better suited for Tensor Processing Unit (TPU)" inference and training. Yet "there still are thousands of models that need to be migrated from TensorFlow", and "Manually migrating all of them would entail hundreds of expert engineering years".

TensorFlow relies on stateful layers and static execution graphs; JAX is functional and stateless. Custom ops rarely have direct JAX equivalents, and migrated code must follow strict internal coding standards. See [Deep learning frameworks: PyTorch, JAX and Keras](#dl-frameworks).

## Why this approach

Tools such as Gemini CLI, Codex CLI and Claude Code have simplified engineers' workflows, the authors write, but for very complex migrations "it is still challenging to produce reliable and high quality output". Early tests on open source models showed API hallucinations, style inconsistency and code that did not build consistently, so the team moved from basic prompts to playbooks.

They split the work across agents because "Single-agent setups struggled with long-horizon tasks, frequently losing context". See [Multi-agent orchestration patterns](#multi-agent-patterns). For the internal models they chose checklists graded by an LLM over numerical equivalence tests, whose setup "can often be as difficult as the migration itself".

## The approach

The system extends an AI-based code migration system Google described earlier (Nikolov et al., 2025).

1. **Playbooks.** Markdown files concatenated into the system prompt: general instructions for Google's monorepo, a style playbook, a task-specific playbook that "was generated by Gemini from official documentation", and a YouTube playbook built from two human-migrated "golden examples" by Gemini, supervised by a human engineer. See [Instruction files](#agent-instruction-files).
2. **Planner.** Dependency discovery uses Kythe, a static analysis tool, instead of an agent, which makes it "deterministic, verified, fast, and computationally cheap". An LLM then builds the plan recursively. Each step should leave buildable code and carries a validation condition.
3. **Orchestrator.** It hands one group of steps at a time to a coder, injects only the relevant playbooks, and decides to retry, skip or abort based on the coder's outcome.
4. **Coder.** A ReAct agent builds and tests its own code and fixes failures. When it declares it is finished, the system prompts it to validate the task. Summaries of each step go to a shared file-based memory bank and are passed to every later coder.
5. **Judge.** For each test model the team manually curated a "Golden Checklist". A judge checks it against the JAX code only, without the TensorFlow source. The score is not fed back to the agents.

## The stack

As of March 2026: all agents use Gemini 3 Pro with a temperature of 0.2; the judge also runs on Gemini 3 Pro. The coder's tools list, read and write files, search code in the Google3 repository, search and replace, auto-fix dependencies, run builds and run unit tests. The target is JAX with Flax Linen, and plans are stored as JSON.

## Results, and how they were measured

- **Checklist quality.** Four configurations ran on six YouTube test models "multiple times (N>10 each)", and "all the migrated code builds". The paper finds "multi_agent_yt_specific is the strongest configuration" (paired t-test, p<0.02), followed by multi_agent, with a significant gap (p<0.02) to the two single-agent configurations. On large_1 the main configuration scored 0.65 against 0.09 for single_agent_baseline; on small_1, 0.95 against 0.66. On the two simplest models, small_1 and small_2, the significant difference between these two configurations "vanished" (p=0.07).
- **Cost.** "the multi-agent configurations take approximately 3-5 times longer than the single-agent configurations".
- **Time.** For two manually migrated in-production models, the team compared a human expert's migration time with the time an expert needed to bring the agent's code to "a trainable model of equal quality": ~16 hrs against ~2 hrs (8x) for model_1, and ~32 hrs against ~5 hrs (6.4x) for model_2. The paper sums up: "We estimate time savings of 6.4x-8x". For small open source models, using human experts' estimates, "the migration speed was increased by a factor of 1.7x".

**Not measured:** "A perfect checklist score does not guarantee correctness." The checklists "primarily measure completeness of the migration", not numerical parity. The speedup is an estimate on two models; the paper does not state the period, how the hours were gathered, or whether these models also built the playbooks. It gives no count of models migrated in production. As many migrated models are not yet deployed, the authors did not account for subtle errors the system may have introduced.

## What failed

- **Single agents.** The baseline "frequently omits loss functions, evaluation metrics, and key logic such as label weighting". With the YouTube playbooks but no planner, the extra context "proved overwhelming, often leading to incomplete migrations" where the agent "declared success despite implementing only a skeleton of the required logic". See [Agent failure modes](#agent-failure-modes).
- **Client-specific playbooks alone.** This domain knowledge "only yielded improvements when coupled with the planner and orchestrator".
- **Overfitting risk.** The playbooks were also generated from the two playbook-generation models, "which carries a risk of overfitting the prompts". The test set excludes them.
- **Coverage.** The evaluated models are "only a small fraction of all the models that have to be eventually migrated".

## What the team would do differently

The paper states lessons and next steps, not things it would redo. Client-specific playbooks "provide a crucial lift, even when derived from just two manually completed examples", and a multi-agent system improves quality "at the cost of higher compute" once models are complex enough. The authors plan debugging agents for training instability and inference latency regressions, and expect "A more precise measure of the impact and time saving" once many migrated models are in production.

The wiki's reading: a judge that never sees the source, and a score the agents never see, keeps the metric usable for comparing designs. See [LLM-as-judge done right](#llm-as-judge).
