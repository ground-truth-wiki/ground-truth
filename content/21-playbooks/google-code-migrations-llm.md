> [!tldr]
> Google built a system that finds references to an ID field across its monorepo, has a fine-tuned internal Gemini model change the code from int32 to int64, and promotes only changes that pass automated checks. Across 39 migrations in twelve months, "74.45% of the code changes and 69.46% of the edits were generated by the LLM". The developers estimated a 50% time saving, which was not measured.

> [!note] From the public record
> Built from Google's own published account, "Migrating Code At Scale With LLMs At Google" (April 2025), linked under Sources with an earlier Google experience report on the same work. ## The problem

An earlier Google experience report on the same work says IDs in the Google Ads code base had to move from 32 to 64 bits "to avoid negative rollover scenarios that could cause outages". The April 2025 paper explains that changing a field's type can require changes wherever the field is referenced, directly or indirectly. It adds that it is a good idea for tests to use values larger than the int32 maximum.

The paper says one ID had been migrated by hand at Google "three years ago", using regular expressions to find references. "This effort took around two years to complete". Regular expressions could miss references or find ones that needed no change, and verifying hundreds to thousands of changes "seriously hinders developer productivity". The experience report says the full effort, done manually, "was expected to require hundreds of software engineering years".

## Why this approach

The authors say data flow analysis or an AST parser could address these accuracy problems. But they call maintaining such logic for code written by thousands of developers over many years "a costly, imprecise and practically intractable approach". They also call rule-based transformation tools such as TXL expensive to maintain. So the team chose "an inaccurate yet practical approach to finding potential references to the ID" and let an LLM bridge the gaps in accuracy.

## The approach

The system runs nightly until no locations are left. For the general pattern, see [Inside coding agents](#coding-agent-internals).

1. **Find.** Kythe, Google's code index, finds references to the ID field, then references to those, up to a total distance of five. The set is deliberately larger than needed. See [Structured and code retrieval](#structured-code-retrieval).
2. **Sort.** Categorizers, such as regular expression checks, label each location not-migrated, irrelevant, relevant or left-over. Developers decide on the left-over ones.
3. **Edit.** For not-migrated and relevant locations, the model gets the whole file with the suggested lines marked, and a language-appropriate prompt. The Java example prompt also asks for large test IDs. It returns diffs, applied with a fuzzy diffing algorithm. Three rounds are tried per file, and a random successful one is kept.
4. **Validate.** Checks run from cheapest to most expensive: a successful model response, more than whitespace changed, the file parses and its AST changed, the model confirms the change was needed, the build passes, regression tests pass. A file that fails goes to developers to migrate by hand.
5. **Review.** Developers inspect and fix the grouped code changes and send them to code owners in Critique, Google's code review tool. See [Human in the loop](#human-in-the-loop).

## The stack

As of April 2025: an internal version of Gemini fine-tuned on internal Google code and data with the DIDACT framework. One fixed version ran at temperature 0.0 for the whole study, with prompting only and no task-specific fine-tuning. Around it: the monorepo, Kythe, AST parsers, build and test infrastructure, and Critique. Languages named include Java, C++, Python and Dart.

## Results, and how they were measured

- **Scale.** The paper reports that "three developers migrated 39 distinct IDs over twelve months using our system", in 595 code changes.
- **Code changes.** 214 (35.97%) were LLM-Only, 229 (38.48%) LLM-then-Human and 152 (25.55%) Human-Only.
- **Edits.** Of 93,574 edits, the LLM made 64,996 (69.46%) and humans 28,578 (30.54%). Edits are counted as Levenshtein edit distance, a proxy for effort.
- **Time.** The developers "estimated a 50% reduction on the total time spent on the migration compared to earlier manual migrations". The paper adds: "We do not have concrete wall-clock effort measurements on the total time spent".
- **The earlier report.** Measured per character against the committed code, it found "80% of the code modifications in the landed CLs were fully AI-authored".

**Not measured:** wall-clock time, and there was no controlled comparison. **Not stated:** compute cost and defects after release. The calendar dates of the twelve months are not stated. The earlier report says: "Whether there is a long-term impact on quality remains to be seen."

## What failed

- **Hallucinations.** The model sometimes only reformatted code, added comments or made irrelevant changes. "Developers had to manually handle such cases, constituting 25.55% of the code changes and 30.54% of the edits."
- **Context window.** Some edits were not made by the LLM because a large file did not fit into the context window, so developers made them by hand. A footnote says newer Gemini versions mitigate this.
- **Languages.** "Dart was not well supported, as the LLM was not trained on enough Dart code".
- **Non-determinism.** Retries sometimes worked, but developers could not predict how many were needed. See [Nondeterminism and reproducible inference](#inference-nondeterminism).
- **Pre-existing tests.** Pre-existing test failures blocked some successful LLM changes until code owners fixed them. Tests using goldens (stored expected outputs) sometimes failed and needed manual work.
- **Rollout.** Two large IDs, ID-30 and ID-32, needed attention from code owners and a slow rollout. "Our system provided no automation or benefits for this step."
- **Reverts.** The earlier report found that "in most cases, the human needed to revert at least some changes the model made that were either incorrect or not necessary".

## What the team would do differently

The paper names its limits: "Our case study does not involve a controlled experiment comparing the LLM-based approach to other techniques". The developers also helped shape the system, a possible source of bias, and the 50% figure is "based on developer perception and estimations, and not on precise time tracking data". The authors think the workflow, "especially using an LLM but verifying its proposed changes through tooling", could carry over to other migrations.

The earlier report adds: "The use of LLMs alone through simple prompting is not sufficient for anything but the simplest of migrations." It also says reviews and rollouts "can quickly become bottlenecks".

The wiki's reading:

- **Let cheap checks decide, and fall back to people.** A model that is sometimes wrong still helps when failures go to a developer, not to review.
- **Count edits, and label time savings as estimates.** See [Measuring the impact and ROI of an AI feature](#measuring-ai-impact).
