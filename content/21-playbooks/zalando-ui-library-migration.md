> [!tldr]
> Zalando's Partner Tech department built a Python tool that uses GPT-4o to move partner-facing B2B applications from one in-house UI component library to another. The team reports "an overall accuracy of more than 90% for the component migration" and an estimated cost of less than $40 per code repository. It adds that LLMs cannot check visual results, so review and visual testing stay necessary.

## The problem

Zalando's Partner Tech department had developed two in-house UI component libraries, each used in different types of partner-facing applications. The post lists the challenges: inconsistent user experience, duplicated effort, two design languages, harder maintenance and longer onboarding. The department decided to migrate these applications to one of the two. "The project's scope encompassed 15 sophisticated B2B applications". Because the libraries differed significantly, the migration "required substantial resources and time."

## Why this approach

The alternative the post names is codemods, "where we need to explicitly code every edge case." Before committing, the team asked: "Would the models understand our custom components?", "Could they carry out the migration with high accuracy?" and "Is there a risk of subtle, hard-to-detect bugs being introduced?" It tested feasibility at an internal LLM hackathon organised by the Zalando research team and Tech Academy. After the hackathon and further testing, "we opted for GPT-4o, which consistently delivered the most accurate transformations." The post does not name any other model.

## The approach

Five iterations led to the method:

1. **Source code.** The model got the source files of a component in both libraries. "This produced inconsistent results with numerous errors."
2. **Interface.** One prompt generated detailed component interfaces; a second migrated usages with them. Accuracy stayed low, with several component attributes not transformed.
3. **Transformation instructions.** Generated mapping instructions were added, such as `variant=primary` to `type="filled"`. These had flaws: they mapped button sizes name for name, but a medium button in the old library looked like a large button in the new one.
4. **Manual verification.** People fixed the generated instructions, such as the size mapping. This helped basic components, but components that needed substantial restructuring still had issues.
5. **Examples.** The team added "examples of increasing complexity", generated by the LLM and verified manually. "The code was transformed with a high degree of accuracy for all the components." See [In-context learning and example design](#in-context-learning).

Because "as the input prompt size grew, the transformation accuracy declined", components were put in logical groups such as "form" and "core", with context kept between 40-50K tokens per group. Prompts put static parts such as examples first and file content last, to benefit from caching (see [Prompt caching and token economics](#prompt-caching)).

A system prompt set an experienced-developer role, code style, error handling conventions and output format: only the transformed file, inside an `<updatedContent>` tag. "When files exceeded the 4K token limit, the output would get truncated mid-transformation." The tool then sent "continue" in the same conversation.

Small changes to the instructions could change results substantially (see [Prompt sensitivity and robust prompt testing](#prompt-robustness)), so the team added LLM-generated examples as automated tests: "These examples served as validation tools and regression tests".

## The stack

As of February 2025. The tool was developed in September 2024; the post says its findings reflect the model's capabilities then.

- **Model:** GPT-4o at temperature 0, which the post says made output "more deterministic and reproducible".
- **Tool:** Python, on the llm library's conversation API.
- **Developer tooling:** continue.dev, to attach source code to prompts instead of pasting it manually.

## Results, and how they were measured

- **Accuracy.** "We achieved an overall accuracy of more than 90% for the component migration", "with even higher accuracy for components of low to medium complexity." The cost section instead says "an accuracy of about 90%".
- **Cost.** From the post's rough averages (~45K tokens per group prompt, ~2K tokens per output file, ~10 component groups, ~30 files per group): "Based on the GPT-4o pricing, this would come to be less than $40 for each code repository." This is an estimate, not a reported bill; prompt caching could lower it.
- **Speed.** "Processing times ranged between 30 and 200 seconds per file, making large-scale migrations time-intensive." The post calls this "not a major issue" because files could be transformed in the background.
- **Development effort.** The team says it built the tool faster than codemods, "which typically require more extensive development time", but gives no time figures.

**Not measured:** the post gives no method, test set or baseline for the accuracy figure, no comparison with manual migration, no actual spend and no count of defects after migration. It does not say how many of the 15 applications were migrated; it only mentions wrapping up "this phase of our UI migration".

## What failed

- **Instructions not followed.** "Even with carefully crafted prompts, LLMs occasionally deviated from the provided instructions or made unexpected changes." The post also reports "plausible-looking but incorrect code".
- **Inconsistent outputs.** Results changed "sometimes simply by rerunning the same prompt on the same file at a different time." See [Nondeterminism and reproducible inference](#inference-nondeterminism).
- **No view of the layout.** "LLMs are unable to verify visual implications of the changes". The libraries use "different spacing scales and grid systems (12 vs 24 columns)", so "the layout may appear broken upon deployment."
- **Project-specific gaps.** Different design philosophies, hard-to-migrate test suites, feature gaps between the libraries and varied styling across applications "often required significant manual work and refactoring".

## What the team would do differently

The post states lessons, not things to redo. Work iteratively, since "there is no universal formula or fixed approach on how to increase the effectiveness of a LLM." Give code examples. Keep people involved: "human oversight and verification is crucial while dealing with LLMs at every stage", including code reviews and thorough visual testing. Evaluate LLM tools before a similar project, and keep prompts "clear and concise."

The wiki's reading: the accuracy figure has no stated method, so a team planning a similar migration should build its own check first, such as a fixed set of real files reviewed by people and visual tests. See [Building eval datasets](#eval-datasets).
